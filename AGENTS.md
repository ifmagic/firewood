# AGENTS.md

## Project Overview

Firewood is a local-first desktop toolbox built on Tauri 2 + React 19 + TypeScript, bundling developer tools: terminal, text/code tools, notepad, image export, translation, and more. UI uses Ant Design; i18n uses i18next.

## Common Commands

- Install dependencies: `npm install`
- Develop: `npm run dev` (frontend) / `npm run tauri:dev` (desktop app)
- Build: `npm run tauri:build`
- Format: `npx prettier --write .` (config in `.prettierrc.json`; CSS uses tab indentation)
- Lint: `npm run lint`
- Type check: `npx tsc -b` (the root tsconfig is a `files: []` reference shell — plain `tsc --noEmit` checks nothing and passes vacuously)
- Frontend tests: `npm test` (single run) / `npm run test:watch` (watch mode), vitest
- Rust tests: `cargo test --manifest-path src-tauri/Cargo.toml`

## Conventions

### Editor (CodeMirror 6)

All text editing scenarios use CodeMirror 6. Monaco is banned (`@monaco-editor/react` / `monaco-editor`) — poor IME compatibility under WKWebView, and CDN loading conflicts with the local-first positioning.

Always reuse `src/hooks/useCodemirror.ts`:

- `variant: 'writing'` (default): long-form writing mode, proportional font stack (used by moxia)
- `variant: 'code'`: code editing mode, monospace font stack + line numbers/folding/bracket matching/completion + light theme; `language` supports dynamic switching between json / html / javascript / plaintext (used by notepad and json-formatter)

Font stacks, line height, IME composition loop prevention, dynamic font-size Compartment reconfiguration, StrictMode double-mount handling, controlled-value sync, and undo history isolation are all encapsulated in the hook — do not reconfigure them in tools. Use `onUpdate` to observe document/selection changes (e.g. status bar stats; inherits IME delay automatically); use `onReady` when you need the view reference (e.g. scroll reset).

Context menus must use `src/components/EditorContextMenu.tsx` (antd Dropdown: cut/copy/paste/select all/find + `extraItems` extension) — do not build your own.

WKWebView (Tauri's webview) hard constraints:

- `@codemirror/view` minimum version 6.43.7, do not downgrade: the WebKit "scroll, then click → viewport jump / caret lands on wrong line" issue was only fully fixed across 6.43.7–6.43.10 (upstream #170/#1384/#1673 family).
- code variant does not use `drawSelection()`: its selection layer relies on getClientRects measurement, which renders wrong under WKWebView; native selection rendering (same as the writing variant) is reliable.
- The code variant enables multi-selection (`allowMultipleSelections` + `rectangularSelection` + `crosshairCursor`): bindings stay stock on purpose — `defaultKeymap`'s Mod-Alt-↑/↓ adds cursors above/below, Cmd/Ctrl+click adds one at the pointer, Alt+drag selects a rectangle. Notepad is the exception: it reserves Cmd/Ctrl+click for its URL opener and opts out of the click gesture with `EditorView.clickAddsSelectionRange.of(() => false)` (multi-cursor there stays on Mod-Alt-↑/↓ and Alt+drag). **Do not rebind Shift-Alt-↑/↓** (some builds did, to add cursors): that is `defaultKeymap`'s copyLineUp/copyLineDown and users of both editors expect it. Because `drawSelection()` is unavailable, only the main range reaches the native DOM selection, so the non-main ranges are painted by `multiSelectionHighlight` (mark decorations for non-empty ranges, an inline widget caret for empty ones — widgets are safe, CM sets `contenteditable=false` itself). Consequence: the code theme has no `.cm-cursor` / `.cm-selectionBackground` layer — the caret comes from `caretColor` and the primary range from `::selection`, so `CODE_CARET_COLOR` / `CODE_SELECTION_BG` are the single source of truth shared by the native and the decorated artifacts. `src/tools/notepad/editor-behavior.test.tsx` pins the bindings and the decorations.
- `src/utils/wkWebViewFocusShim.ts` must be kept, installed at startup in `main.tsx`: the Safari 26 engine ignores `focus({preventScroll: true})` and scrolls the old caret back into view; CM's built-in Safari-26 workaround depends on the `Version/<n>` token in the UA, which Tauri WKWebView's UA lacks, so it always fails. The shim wraps `focus` to save/restore ancestor scroll positions on `preventScroll: true` calls — removing it reintroduces "long document scrolled far, click → viewport jumps back to the old caret line". Dev verification: the `JumpDebugger` overlay in json-formatter (auto-mounted under `import.meta.env.DEV`).
- JSON text transforms (pretty-print / unescape) live in `src/utils/jsonText.ts` and are shared by json-formatter, notepad's context action and text-diff — do not add per-tool variants (notepad once had a character-level fallback that stripped whitespace outside strings, mangling prose and JSONC comments).

### Terminal (xterm.js)

- Forced repaints go through `forceTerminalRedraw` in `src/tools/terminal/index.tsx`: in @xterm/xterm 6.0.0 a same-size `Terminal.resize()` is a no-op (`CoreBrowserTerminal` early-returns) and a same-size `TIOCSWINSZ` delivers no SIGWINCH, so it round-trips the width (`resize(cols+1, rows)`, then back). Both resizes take the full renderer path (row rebuild + dimension recompute) and notify the PTY, so TUI apps redraw exactly as they do on a window resize; the buffer reflow round-trips losslessly. **The two resizes must not run in the same JS task**: the browser only runs style/layout/paint once per task, so a same-frame round-trip is a net-zero layout change and WKWebView keeps its stale composited output — the ghosting survives, making the refresh button look dead. `forceTerminalRedraw` therefore grows one column synchronously and restores it on the **second** `requestAnimationFrame` (a single rAF is not enough — rAF callbacks run before that frame's style/layout, so the intermediate state would never be painted). The one-frame-wide intermediate column is clipped by the container's `overflow: hidden`. The cols round-trip alone is NOT enough to clear every ghost: it only re-layouts xterm's internals (`.xterm-screen` grows one clipped cell), while the elements a real window resize re-layouts — the host div, `.xterm`, and above all `.xterm-viewport` (the WebKit async-scrolling node) — keep their exact size, so WKWebView's UI-side compositor keeps serving cached tiles for that subtree and full-screen TUI ghosts (e.g. a commit editor's input box) survive while a manual window shrink/grow clears them. The intermediate frame therefore also forces a host-level invalidation: `tab.div` gets `width/height: calc(100% - 1px)` plus `transform: translateZ(0)` for that one frame (real subtree re-layout + a fresh compositing layer that must be re-rasterized), and the restore writes the exact inline values back — `100%`, never `''` (clearing the inline height collapses the terminal to zero). Host styles are dropped unconditionally on restore even when the term-level restore stands aside. Re-entrant requests while a round-trip is pending are ignored (`redrawPending`), and the restore leg aborts if an external resize (fit on container/font change) has taken over the intermediate size. The header refresh button, the `devicePixelRatio`-change fallback, and the remount DPR check all go through `refreshTerminalDisplay` (fit + `forceTerminalRedraw`). The app-level DPR watch exists because xterm's built-in `ScreenDprMonitor` never notifies the PTY.
- Intrinsic xterm behaviors the round-trip relies on (onResize firing per real size change, `renderRows` doing full `replaceChildren` row rebuilds, same-size resize being a no-op) are pinned by `src/tools/terminal/real-xterm.test.ts`, which exercises the real `@xterm/xterm` package instead of the page-level mock.
- PTY resize notification lives solely in each tab's `onResize` handler; `fit()` never invokes `resize_pty` itself.
- Never call `fit()` on a hidden/unmounted tab: its measurements are garbage (`display: none` plus the inline `height: 100%` host parses as ~100px) and can shrink the PTY to a few rows.

#### Windows (ConPTY)

`src-tauri/src/pty.rs` has two backends behind identical `PtyManager` verbs (`create_session`/`write`/`resize`/`read_output`/`close_session`): the bespoke `fork` + `posix_openpt` path on unix, and **ConPTY** (Windows 10 1809+) via `portable-pty` on Windows — declared as `[target.'cfg(windows)'.dependencies]`, so unix builds never compile it. Both emit the same `pty:data:<id>` / `pty:exit:<id>` event stream, so the frontend renders both without platform branches; `decode_utf8_stream_chunk`/`flush_pending_utf8` are shared because ConPTY also emits UTF-8 and can split a code point across reads (that is why the Rust tests are `#[cfg(test)]`, not `#[cfg(all(test, unix))]`). The one contract difference is **when** a failed launch surfaces: unix reports it in-band (exec status pipe → `pty:data` + `pty:exit`, i.e. the "Shell exited" banner), Windows returns it synchronously from `create_session` (the error overlay). Both front-end exits already existed for the unix path, so this is a timing difference, not a new code path — do not "fix" it by forcing one channel on both.

- **Lifetime rules differ, and the difference is load-bearing.** On unix, `close(master_fd)` ends the session and unblocks the reader; the reader polls with a 500 ms timeout so it can also observe the `running` flag. On Windows the pseudoconsole is held by the **master** (`ConPtyMasterPty`) and the reader is a plain blocking read, so the _only_ thing that unblocks an in-flight read is dropping the master — that _is_ `ClosePseudoConsole`, which makes the pipe report EOF. `WindowsPty::close()` therefore drops the master first, then terminates the shell through `child.clone_killer()` and reaps it with a **bounded** `try_wait` loop (mirroring unix `reap_child`): `Child::wait()` has no timeout and `close_all()` runs synchronously on `ExitRequested`, so an unkillable shell must not be able to block application exit. Every close path drops the pty _before_ joining the reader; joining first can hang. `portable-pty`'s slave owns nothing once `spawn_command` returned, so it is dropped immediately (upstream's own example).
- The child environment is rebuilt explicitly — `env_clear()` + every `std::env::vars_os()` entry + `TERM=xterm-256color` + `COLORTERM=truecolor` — instead of relying on portable-pty's inherit-vs-replace semantics: a replaced environment would strip `PATH`.
- Windows shell knowledge lives in `PtyManager`: `get_default_shell()` prefers `pwsh.exe`, then Windows PowerShell, then `COMSPEC` (never `COMSPEC` first — it is always `cmd.exe`). That preference is a deliberate **deviation** from VS Code, whose Windows default has historically been Windows PowerShell 5.1 — it is not claimed as parity. `list_shells()` probes the well-known install locations (pwsh, PowerShell, `cmd`, `wsl`, Git for Windows machine-wide + per-user, MSYS2, Cygwin) and returns full paths, because Windows has no `/etc/shells`; the PowerShell path comes from `windows_powershell_path()` (do not re-inline it). `windows_shell_args()` supplies the per-family interactive flags (`-NoLogo` for PowerShell, `--login -i` for Git Bash/MSYS2) that stand in for the unix `-l`. `windows_working_dir()` prefers `USERPROFILE` over `HOME`: a git-bash `HOME` (`/c/Users/me`) is a valid POSIX path but not a valid `CreateProcessW` cwd.
- Those three decisions are split so the **policy** is unit-testable off Windows: `shell_args_for()` (name → flags), `dedupe_paths_case_insensitive()` and `choose_windows_working_dir()` (injected `is_dir`) are `#[cfg(any(windows, test))]` and covered by `cargo test` on any host, while the `cfg(windows)` wrappers only resolve names and probe the filesystem. Keep new Windows policy on that side of the line — it is the only part of this backend a macOS dev machine can actually run.
- **Clipboard parity** (`attachClipboardKeyHandler` in `helpers.ts`, non-macOS only): xterm.js encodes a bare Ctrl+C/Ctrl+V as `\x03`/`\x16` and then `preventDefault()`s the keydown, so on Windows/Linux the browser's native copy/paste never runs and the selection is silently uncopied. Returning `false` from `attachCustomKeyEventHandler` makes xterm stand down _without_ cancelling, which lets the DOM `copy`/`paste` events fire into xterm's own handlers. Ctrl+C copies only when `term.hasSelection()` (otherwise it still reaches the shell as SIGINT, VS Code's rule); AltGr (Ctrl+Alt) is never claimed, and `event.code` covers layouts whose letter keys are not latin. **Ctrl+Shift+C/V are not a copy/paste path**: xterm has no binding for them either, so they fall through to whatever the host browser does (in WebView2 Ctrl+Shift+C can be the DevTools accelerator) — the supported chords are Ctrl+C/Ctrl+V, and the docs/test comments must not claim otherwise. macOS keeps the untouched native Cmd+C/V pipeline — do not "unify" this to both platforms. `real-xterm.test.ts` pins the mechanism against the real xterm (encoder + `defaultPrevented` + the selection-gated `copy` listener); `helpers.test.ts` pins the chord policy.
- UI platform gates: the footer hint is `terminal.hintMac` / `terminal.hintNonMac`, and the shell picker's starting directory comes from `getShellDirectory()` (both separators, `C:` rewritten to `C:\`, `''` → dialog default) instead of the old hardcoded `/bin`.
- **Verification boundary**: nothing in this backend can be _executed_ off Windows — ConPTY needs a real Windows 10 1809+ host. Local checks are: `npm test` (chord policy + hint + the real-xterm mechanism), `cargo test` (the cfg-free `shell_args_for`/`dedupe_paths_case_insensitive`/`choose_windows_working_dir` policy + the UTF-8 splitter), and `cargo check --target x86_64-pc-windows-msvc`, which type-checks the `cfg(windows)` code but needs the target installed **and network access** to fetch the Windows-only crate sources (it cannot run offline). A networked Windows check is therefore mandatory before trusting a change here: build/spawn each shell family, close a tab while output is streaming, and quit during a live session.

### Window Titlebar & Always-on-Top Pin

- macOS uses `titleBarStyle: "Overlay"` via `src-tauri/tauri.macos.conf.json` (platform configs merge with RFC 7386 JSON merge patch — **arrays are replaced whole**, so that file duplicates the full window config plus the style). The webview extends under the transparent titlebar; native traffic lights stay top-left.
- `npm run tauri:dev` runs `tauri dev --config src-tauri/tauri.dev.conf.json`, and `--config` merges **last** (over base + platform config, via `TAURI_CONFIG` in tauri-codegen). Because its `app.windows` array also replaces the array whole, `tauri.dev.conf.json` must duplicate the full window config (including `titleBarStyle` and `dragDropEnabled`) or dev silently loses those settings — this is exactly why Overlay once appeared "not to take effect" despite full restarts. Sync rule: any window-config field present in one config must stay identical across every config file that carries it; cross-platform fields live in all three (`tauri.conf.json`, `tauri.macos.conf.json`, `tauri.dev.conf.json`), platform-specific additions (e.g. `titleBarStyle`) go in the platform file and the dev file only. `src/tauri-config-sync.test.ts` is the executable guard. Trade-off note: the dev config's window array exists solely to title the dev window "Firewood Dev" while keeping Overlay parity — dropping that title override would let base+platform config flow through and eliminate the dev duplication entirely (cost: the dev window would be titled "Firewood").
- `src/App.tsx` mounts `<TitleBar />` above the sidebar/content `Layout` inside `.app-shell` (see `src/App.css`). **The shell needs `width: 100%`**: `#root` is a ROW flex container, and `antd`'s `.ant-layout-content { width: 0; flex: auto }` collapses the tool pane to width 0 (white screen) if the shell is allowed to size to its content instead of filling the row. The shell also uses `overflow: hidden` so the taller-than-row sidebar (see below) can't page-scroll.
- `src/components/TitleBar` renders the 28px top strip (macOS only): it is the window drag surface and hosts the global always-on-top pin button at the far right. It must NOT render its own app title: `titleBarStyle: "Overlay"` only sets `titlebarAppearsTransparent` + `FullSizeContentView` (see tauri-runtime-wry) — the native window title still shows next to the traffic lights, so a web-side title would duplicate it. The platform guard lives in a wrapper component so no hooks/window-API calls run off macOS.
- **The strip does NOT rely on Tauri's injected drag.js despite carrying `data-tauri-drag-region`** (kept as an inert fallback attribute). drag.js starts `performWindowDragWithEvent` on the FIRST mousedown of a double-click, but the JS→IPC→Rust round-trip means AppKit's drag session often starts only after the first mouseup was already delivered — a performDrag started with the button already up swallows the NEXT mousedown/mouseup pair, i.e. the second click of the double-click. The second click never reaches the webview, drag.js's mouseup leg (detail===2 → `internal_toggle_maximize`) never fires, and double-click-to-zoom is dead (dragging still works because a held drag outlives the IPC latency). The strip therefore takes over pointer handling itself: direct left mousedowns `stopPropagation()` so drag.js's document listener never runs; dragging calls `getCurrentWindow().startDragging()` only after the pointer moves ≥4px while held (tao's `drag_window` explicitly supports invocation from a mouseDragged event — it synthesizes the LeftMouseDown itself); double-click zooms via the native `dblclick` event + `toggleMaximize()` (tao → native `NSWindow.zoom`, which restores the pre-zoom frame). Behavior is pinned by `src/components/TitleBar/TitleBar.test.tsx` (drag.js isolation, drag threshold, one-shot tracking, dblclick zoom, pin-button exclusion).
- The pin itself is the shared `PinToggle` component (`src/components/PinToggle`; `placement` is a **required** prop — antd's default centered "top" is the viewport-edge footgun this file documents, so each consumer must name its safe side): `variant="titleBar"` + `placement="left"` in the macOS TitleBar strip, `variant="sidebar"` in the sidebar header on Windows/Linux — trailing the view menu when expanded (`placement="bottom"`), stacked under the brand when collapsed (`.siderCollapsed .logoWithPin` turns the header into a column; the class is applied together with the pin, so macOS collapsed keeps its original 60px header; the 56px rail cannot fit brand + pin side by side, so the pin grows the header instead of relocating). It deliberately does **not** live in the settings footer: a window toggle parked next to Settings reads as a second settings button, far from the window chrome it controls (this was a real Windows complaint). The **non-macOS** expanded sider is 220px (macOS stays 200px — its header has no pin) with 8px header side padding, because the header hosts brand + view menu + pin and 200px would truncate "Firewood": CoreText measurement puts the brand at ~67px against ~78px of text room at 220px (~10px slack). The Windows fallback font (Microsoft YaHei) could not be measured locally — if it ellipsizes there, bump the non-macOS width to ~228 rather than shrinking padding. **Exactly one instance may mount per platform** (two would fight over one window state) — the XOR invariant, plus the header-not-footer slot, is pinned by `src/components/Sidebar/Sidebar.test.tsx`. Platform gating uses `isMacPlatform()` (`src/utils/platform.ts`, sync UA sniff so it can gate the render tree); the window mutation is guarded separately by the runtime check in `useAlwaysOnTop`.
- Sidebar height is `100%` (not `100vh`): inside `.app-shell` the content row is `100vh − titlebar`, so a hard `100vh` would overflow the row by the titlebar height. On Windows/Linux the native title bar remains and the pin surfaces in the sidebar header — the app's first webview row, the closest analogue of the macOS strip (via the shared `PinToggle`).
- Pin state is persistent (`useAlwaysOnTop` → localStorage `firewood-always-on-top`, type-guarded via `usePersistentState`'s validator) and re-applied on launch. The required permissions `core:window:allow-set-always-on-top`, `core:window:allow-start-dragging`, and `core:window:allow-toggle-maximize` are in `src-tauri/capabilities/default.json` — none is in `core:window:default`. The sync-throw failure mode of `getCurrentWindow()` outside Tauri is pinned by `src/hooks/real-tauri-window.test.ts`.
- The titlebar pin's Tooltip must use `placement="left"`. Default `top` centers the popup on a button 12px from the right edge; during rc-trigger's measure/align phase the popup momentarily overflows the viewport, the document becomes scrollable, and WKWebView flashes its scroll indicators — perceived as the whole window shaking right+bottom, lasting until rc-trigger re-aligns, recurring on every hover. As of this writing the pin is the only button whose default top popup overflows (other default-placement tooltips — json-formatter, translate, numbox — sit away from viewport edges); debug probes with short popups will NOT reproduce this. Any future element pinned against a viewport edge with a centered popup needs the same treatment.

### Tauri Rust Commands

New commands follow the two existing patterns: `pty.rs` (stateful resource pool) and `translate.rs` (stateless call):

- Stateful resources: wrap in `Arc<Manager>` + `parking_lot::Mutex` (not `std::sync::Mutex`), inject state via `Builder::default().manage(...)` in `main.rs`, retrieve with `State<'_, Arc<YourManager>>` in command signatures.
- All commands return `Result<T, String>`; propagate errors with `.map_err(|e| format!("...: {}", e))?`.
- Exit cleanup: call `close_all()` in the `RunEvent::ExitRequested` callback.

### SQLite (rusqlite)

moxia uses `rusqlite` (with the `bundled` feature) to manage SQLite on the Rust side, one `.moxia` file per book:

- The connection pool is managed by `MoxiaManager` (`Mutex<HashMap<PathBuf, Connection>>`); `tauri-plugin-sql` is not used.
- Rust-side `Connection::open` is not constrained by `capabilities` fs scopes — it can read/write any path the user has OS permission for.
- Migrations are built into `src-tauri/src/moxia/migration.rs`; append new table schemas as versioned migrations.
